# Product Requirements Document

Use a short product title. Do not add a document-type prefix.

Write section prose in ASD-STE100 per `.agents/references/asd-ste100.reference.md`. Write
functional requirements and acceptance criteria in EARS per
`.agents/references/ears.reference.md`.

Adapt the sections to the topic. Omit a section only when it is clearly not
applicable.

## Purpose

State what this specification defines and why it matters.

## Problem and context

Describe the pain, constraint, or driver. Use short bullets.

## Goals

List measurable outcomes. Each goal must be testable.

## Non-goals

List explicit boundaries. State what this work does not change.

## Functional requirements

Write each requirement as an EARS sentence. Number each requirement as `FR-1`,
`FR-2`, and so on.

Use a table only for attributes that are not a system response.

## Non-functional requirements

Cover the relevant attributes, such as retention, security, performance,
compliance, and cost.

Use EARS when the attribute is a system response. Keep a pure metric as a
number.

## Acceptance criteria

Write each criterion as a full EARS sentence. Number each criterion as `AC-1`,
`AC-2`, and so on.

- [ ] `AC-1`: Write the EARS sentence.
- [ ] `AC-2`: Write the EARS sentence.

## Open questions

Number the decisions that are still open. Remove this section when no question
remains.

## Links

List the parent request, related documents, dependencies, and affected
artifacts.
